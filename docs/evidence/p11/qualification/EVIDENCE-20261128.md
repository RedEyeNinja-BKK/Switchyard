## 1. What actually produced the pinned-workstream 503

The pinned workstream (`qual-lite31-t1`, model `direct-google-gemini-3.1-flash-lite`)
recorded:

```
Backend request failed (HTTP 503 Service Unavailable): openai at
https://switchyard-vm.tailc8ef7b.ts.net/v1 (model=direct-google-gemini-3.1-flash-lite).
raw='Error code: 503 - backend temporarily unavailable'
```

That text is the **last** attempt, and it is a local refusal. Switchyard's own
journal for the same request separates the two events:

| time (UTC) | correlation | outcome | duration | error class / message |
| --- | --- | --- | --- | --- |
| 04:35:53.042 | `sy3dabd3bf57ff49110000012b` | 503 | 1630.8 ms | `provider_unavailable`, `upstream_error (HTTP 503 Service Unavailable)` |
| 04:35:53.455 | `…12d` | 503 | 4.6 ms | `local_unavailable`, `backend temporarily unavailable` |
| 04:35:54.448 | `…12e` | 503 | 2.6 ms | `local_unavailable`, `backend temporarily unavailable` |

- **An upstream request was attempted.** Attempt `…12b` spent 1.63 s and came back
  as an upstream HTTP 503; this is a provider-side event, not a local admission
  rejection.
- **The retries never left the host.** `…12d` and `…12e` finished in 4.6 ms and
  2.6 ms with `selected_model=""` and `upstream_request_id=""`. The lane's failure
  cooldown (default 5 s; `failure_cooldown_ms` in the target's client entry) refused
  them locally, which is what Turnstone surfaced to the operator.
- The request was **not** refused by context or by the daily allowance: the same
  log lines carry `ctx_estimated_input_tokens=71643`, `ctx_effective_limit=1048576`,
  `ctx_shadow_decision="admit"`, and the target's counter read
  `{"day":20784,"spent":368,"limit":500}` (132 requests left) four minutes earlier.
- The 179-token figure seen earlier is a **different, successful** request at
  04:35:53.240 (`prompt_tokens=179`, `completion_tokens=3`), i.e. the small probe.
  It is not the failing request.

Conclusion for this event: **provider 503 on a ~72k-token, 19-tool request, followed
by a local cooldown refusal of the two immediate retries.** Throughput/TPM played
no part in it, and the surfaced message hides the upstream leg.

## 2. What actually limits a multi-turn agent loop on these lanes

With the pinned workstreams doing real work, each model call carries ~79–80k input
tokens (persona, tools, conversation). The target declares
`requests_per_minute = 15` and `input_tokens_per_minute = 250000`, so roughly
**three calls per minute** fit, and the counter charges the gross prompt even when
most of it is cached by the provider (`cached_tokens` reached 77,699 of 80,115).

Observed on both Lite candidates: 3–4 successful calls, then Switchyard refuses
with `per-minute input_tokens_per_minute budget … is full; it clears in about 19-22s`,
and Turnstone ends the turn in `error`. The retry storm in the same window is
visible as ~20 refusal lines per three minutes.

This is an **orchestration/throughput suitability** fact about the harness shape,
not a model defect, and it is why a single message cannot always finish a
five-call task: the run must be resumed after the minute window clears.

### 6.2 Existing retry machinery (measured, not assumed)

- Turnstone reissues a failed completion at most twice
  (`MAX_COMPLETION_REISSUES = 2`), with a fixed base delay of 1 s doubling per
  reissue (`_RETRY_BASE_DELAY = 1.0`, session.py; model_turn.py uses 0.5 s with
  jitter). Total pacing inside one turn is therefore ~1-3 s.
- Switchyard's minute-allowance refusal names its wait in prose only
  ("it clears in about 19-22s") and sets **no** `Retry-After` header: the value
  exists internally (`retry_after_secs`) but is not emitted.
- There is no supported workstream setting for retry pacing, and no scheduler
  that resumes an errored workstream. `auto_approve` (used here) removes approval
  stalls only.

So **no existing supported configuration can pace or resume autonomously**. The
current behaviour spends all three attempts inside ~3 s and then errors, even
though the lane is servable again seconds later.

### 6.3 Minimal change proposed (not implemented)

1. **Switchyard**: emit `Retry-After: <secs>` on the minute-allowance 429. The
   number is already computed (`retry_after_secs` in `lib.rs`), so this is a
   header, not a policy change.
2. **Turnstone**: for a provider 429 that carries `Retry-After`, use it as the
   backoff for the existing bounded reissues (cap at ~60 s, keep
   `MAX_COMPLETION_REISSUES = 2`, still cancellable).

Together these let one turn wait out the window instead of burning its attempts.
Either alone is insufficient: Turnstone cannot guess the wait, and a header no
client reads changes nothing.

A second, smaller defect is worth recording: the surfaced error is the **last**
attempt only (`backend temporarily unavailable`), so the originating provider 503
is lost. Preserving the first attempt's cause alongside the terminal one would
stop local cooldowns masquerading as the provider fault.

## 7. Token accounting: gross versus cached

Measured on these lanes: the pacing ledger charges the full input size, and a
provider cache hit does not reduce it. Concretely, three calls of ~80k tokens
exhaust the 250k minute budget while the provider reports `cached_tokens` of
77,699 of 80,115. No change is proposed: Google's per-model per-minute semantics
for cached content are not established here, and the owner's rule is that
accounting does not move without verified provider semantics.
