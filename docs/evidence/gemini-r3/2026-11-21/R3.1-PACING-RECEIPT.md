# R3.1 — per-minute admission deployed (2026-11-21)

R3 made the free pool selectable. R3.1 makes it *paced*: the provider's minute windows are
now enforced before a request leaves, so a burst cannot spend a day's allowance in a single
minute and a retry cannot become an unbudgeted request.

## What changed

| Layer | Change |
| --- | --- |
| `crates/libsy-llm-client/src/allowance.rs` | `WindowLimits`, `GovernorKey`, `QuotaGovernor` (60 s sliding window, requests and input tokens enforced independently), `PacedQuota`, `PacingError`, `estimate_input_tokens`. A granted reservation can be released only before the request is sent. |
| `crates/libsy-llm-client/src/client.rs` | `send_once` paces **before** the daily reservation and releases the minute slot if the daily allowance then refuses. A throttle is never retried in-call. |
| `crates/protocol/src/client.rs` | `MinuteAllowanceThrottled { model, scope, retry_after_secs }`, classified `RateLimited` and crossable, never `AccountQuota`. |
| `crates/switchyard-server/src/lib.rs` | Renders as `429 rate_limit_error` / `minute_allowance_throttled`. |
| `crates/switchyard-runner/src/config.rs` | `requests_per_minute` and `input_tokens_per_minute` per target; one shared governor per deployment; keys are `(quota group, physical model, feature)` so every alias of one model draws on one window; a token window requires a per-request ceiling at or below it; targets sharing one model must state one value. |

| `gemini-3.1-flash-lite` | 12 | — | 250,000 |

The Gemma ceiling moved down because a request larger than a whole minute can never be
admitted; the ceiling now sits at the window, so admission skips the leg instead of
spending a call on a 429.

## Live proof

1. **Burst on one leaf** (`direct-google-gemma-4-26b-a4b-it`), three ~5,000-token prompts:
   the first returned 200 (`prompt_tokens: 4017`), the second returned Google's own
   `503 UNAVAILABLE`, the third was refused by the armed capacity cooldown. The provider
   refusals are not the governor's, but they reserve exactly as they should.
2. **Refusal proof, zero provider calls**: two further requests of ~8,000 estimated tokens:

   ```
   attempt 1  429  0.01s  rate_limit_error / minute_allowance_throttled
              "per-minute input_tokens_per_minute budget for gemma-4-26b-a4b-it is full;
               it clears in about 30s"
   attempt 2  429  0.00s  rate_limit_error / minute_allowance_throttled
              "… it clears in about 23s"
   ```

   The window already held the two earlier attempts (5,001 + 5,001 estimated), so 10,002 +
   8,001 exceeded 14,400. `retry_after` decayed 30 s → 23 s across the seven-second gap,
   which is the oldest reservation expiring — a sliding window, not a fixed clock minute.

   Neither request reached Google: the routing log has no entry for that model in the window
   (it records completed calls only), and both responses carry no upstream status.

3. **Background traffic is untouched.** `smart-nt` is live on real work: at
   `22:27:38Z` it served a 62,345-token prompt from `gpt-6-luna`. That traffic is
   uncleared, so it never reaches a Google leg; the governor bounds the Google lanes
   without slowing it.

## Known limits

- The governor is in-process. A restart under-counts for the remainder of the current
  minute; a minute is not worth a lock and a disk write on every request.
- Input tokens are estimated from the outbound body (characters/4, `data:` payloads
  excluded). Measured bias on the proof prompt: 5,001 estimated vs 4,017 actual, i.e.
  conservative — the refusal comes slightly early rather than late.
- Vision requests on a paced model are paced by the request axis only; inline binary is not
  modelled as prompt tokens.
