pub fn provider_request_id(document: &Value) -> Option<String>
Expand description

The provider’s request id, from every location providers are known to use.

Priority is provider-authored evidence, most structured first:

  1. a structured field nested under error (the OpenAI shape);
  2. a structured field at the top level (the Anthropic shape);
  3. the provider’s own message prose, e.g. DeepSeek’s (request_id: 5502af93-…).

A bare top-level id is deliberately never read: that is the response object id (resp_…, chatcmpl_…), and reporting it would put a value beside the provider’s logs that does not exist there.

A document that is a JSON string is a body that was not JSON at all: the server preserves such a body verbatim and hands it over as a string, so its prose is the only place an id can be. That case is handled here rather than at each call site, because a call site that forgot it would drop the id silently — which is exactly what happened when this rule was consolidated out of the server.
